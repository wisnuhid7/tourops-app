I revised the test-data plan so Tourops works with **direct clients, family/group organizers, and tour leaders—not travel agencies**. The supplier, itinerary, quotation, acceptance, booking, and confirmation workflows remain intact. 

# Tourops Test Data Population and End-to-End Testing Instructions

## Direct Client, Tour Leader, Supplier, Quotation, and Booking Workflow

---

# 1. Purpose

Create a complete non-production test environment for Tourops.

The Replit developer must populate the database in the correct sequence so the entire application can be tested from the beginning of the business process.

Tourops does **not** use a travel agency as the client in this scenario.

The client may be:

1. An individual booking for themselves
2. A family organizer booking for a family
3. A group organizer arranging travel for a private group
4. A tour leader organizing a group tour
5. A company or organization arranging travel for its members

The first complete test scenario must cover:

1. Super Admin creates an Admin user.
2. Admin creates internal company users.
3. Admin creates supplier companies.
4. Admin creates supplier user accounts.
5. Supplier users complete their company profiles.
6. Admin reviews and approves suppliers.
7. Suppliers create services and rates.
8. Admin creates a tour itinerary using supplier services.
9. Admin configures pricing rules.
10. A direct client or tour leader creates an account.
11. The client selects a tour itinerary.
12. The client selects the departure date, departure city, group size, hotel choice, and room requirements.
13. The client requests a quotation.
14. Tourops calculates the complete tour price.
15. Admin reviews and approves the quotation.
16. The client receives and accepts the quotation.
17. The quotation is converted into a booking.
18. Suppliers receive requests for the services assigned to them.
19. Suppliers confirm or reject their assigned services.
20. Tourops Operations completes the booking confirmation process.

The test data must be:

* Realistic
* Connected
* Reusable
* Repeatable
* Safe for the staging environment
* Clearly identified as test data

# 5. Seed Script Requirements

The seed process must be:

* Repeatable
* Idempotent
* Transactional
* Logged
* Safe for staging
* Blocked in production

## 5.1 Idempotent Requirement

Running the seed more than once must not create duplicate records.

Use permanent test codes such as:

```text
TEST-ADMIN-001
TEST-CLIENT-001
TEST-TOURLEADER-001
TEST-SUPPLIER-TRANSPORT-001
TEST-SUPPLIER-HOTEL-001
TEST-ITINERARY-001
TEST-QUOTE-001
TEST-BOOKING-001
```

Use database upsert operations where appropriate.

## 5.2 Production Protection

The test-data process must stop immediately when:

```text
NODE_ENV=production
```

It must also stop when the connected database is identified as a production database.

## 5.3 Transaction Requirement

Each seed phase must run inside a database transaction.

If a phase fails:

1. Roll back the failed phase.
2. Preserve successfully completed previous phases when appropriate.
3. Record the error.
4. Display the failed record.
5. Display the failed seed phase.
6. Do not leave incomplete dependent records.

# 14. Supplier Invitation and Approval Test

For every supplier:

1. Admin opens the supplier.
2. Admin selects “Invite Supplier User.”
3. Admin enters the user details.
4. Admin assigns Supplier Administrator.
5. System connects the user to the correct supplier.
6. System creates the invitation.
7. Test-email service captures the invitation.
8. Supplier opens the invitation.
9. Supplier creates a password.
10. Supplier accepts the terms.
11. Supplier signs in.
12. Supplier sees only their company.
13. Supplier completes the profile.
14. Supplier uploads test compliance documents.
15. Supplier submits the profile for approval.
16. Admin reviews the profile.
17. Admin approves or rejects the supplier.
18. Approved supplier status changes to Active.
